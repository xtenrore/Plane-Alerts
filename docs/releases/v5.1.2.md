# Plane Alerts v5.1.2

Plane Alerts v5.1.2 is a production hotfix for the v5.1 3D predictor wrapper chain. It restores the intended v5.1 behavior and does not introduce a new physical prediction model.

## Fixed

v5.1 introduced the `altitude_relevance` predictor option, but the already-installed v4.6 confidence wrapper still exposed the older function signature. In production the critical-timing wrapper forwarded the new keyword into `predict_trajectory_v46`, causing every affected CPA calculation to fail with:

`TypeError: predict_trajectory_v46() got an unexpected keyword argument 'altitude_relevance'`

v5.1.2 updates that wrapper to accept and forward the v5.1 option. It also keeps `user_altitude_m=None` intact so unknown observer elevation continues through the v5.1 conservative uncertainty path instead of being silently treated as sea level.

## Regression protection

The release adds a regression that recreates the production call chain:

`monitor -> critical timing wrapper -> v4.6 confidence wrapper -> v5.1 trajectory predictor`

The test verifies both `altitude_relevance=False` and `altitude_relevance=True` are accepted and forwarded, and verifies unknown observer elevation remains unknown.

## Prediction identity

Application version: `5.1.2`.

Physical prediction version remains `5.1-3d-proximity`.

Runtime AI and AGY remain non-authoritative for trajectory, CPA, ETA, pass/no-pass, qualification, cancellation and alert timing. No paid runtime service is introduced.

## Production verification required

Before v5.2 begins, both Railway services must run the exact tested v5.1.2 commit. Main-service verification must show live CPA calculations without the wrapper `TypeError`, normal five-second cadence, healthy Telegram/runtime startup and no regression in the terminal-arrival guards.

## Rollback

The immediate application rollback target is v5.1.1 commit `9af0d12a22d6021da9129543b53fd62220802b56`, but that build is known to fail CPA calculations through the production wrapper chain. If rollback is necessary, operators should prefer the last healthy pre-v5.1 production release rather than knowingly restoring the v5.1.1 runtime error.
