# Plane Alerts v5.5.4 — Provider-First Destination Path Guard

## Summary

v5.5.4 is a focused Railway production reliability patch for the persistent airport-arrival false-alert problem. It removes the accumulated route-history, expected-turn and runway/terminal veto chain from live alert authority and replaces it with one cached provider-first destination layer followed by deterministic destination/path geometry.

The target failure is an arriving aircraft that points toward the observer long enough for a straight-line CPA to look close, then turns or lands at its destination before ever reaching the observer. IST/LTFM and LTBA are regression examples of the general solution rather than airport-specific production exceptions.

## Destination resolution

- Existing ADSB.lol route information is used as the primary destination source.
- ADSBDB is used as an independent additional/fallback source.
- Provider results are live-position sanity-checked before they can carry destination authority.
- Agreement between usable providers is recorded as provider agreement.
- A single usable source may be used conservatively.
- A genuinely ambiguous provider conflict fails open to live deterministic trajectory rather than choosing an arbitrary provider.
- If providers disagree but live terminal geometry identifies exactly one physically strong nearby destination while the competing destination is materially farther away, Plane Alerts may resolve that conflict from live geometry rather than provider priority. This covers the existing THY2GN IST-vs-SJJ Error Museum evidence without blindly trusting either source.
- Unavailable providers also fail open.
- Positive, negative and conflict results are cached with bounded process-local storage.
- Provider calls run only as bounded background tasks; the five-second monitoring path never awaits them.

## Deterministic destination/path qualification

When a reliable destination exists, Plane Alerts checks live aircraft position, destination position, observer position, speed, altitude/descent, predicted CPA and the projected path.

An initial approach candidate may be held when deterministic geometry shows that:

- the projected path reaches the destination landing area before the observer pass,
- current speed/distance indicate the destination airport is physically reached before the observer pass while the aircraft is in terminal/descent context, or
- continuing to the projected observer CPA would move the aircraft materially farther from its known destination.

This does not make destination metadata absolute. Fresh physical entry inside the configured observer radius always overrides destination suppression. If the destination airport itself lies inside the observer radius, live trajectory also remains authoritative because the arrival can genuinely enter that radius. A clear go-around/diversion or sustained material divergence from the reported destination releases destination authority so live trajectory can qualify a later genuine pass.

A brief 5–10 second heading away from the airport is explicitly not enough to invalidate a plausible arrival destination; that short-heading assumption was part of the original false-alert failure mode.

## Simplified authority model

The production worker no longer installs the old live arrival authority chain composed of route guard v2, v4.2 terminal/history qualification, v4.3 route requalification and v4.7 airport/runway qualification.

Bounded route-history observation remains available for Prediction Lab, analytics and diagnostics. Airport/runway reference logic also remains available for diagnostics. Neither is required to decide that an arrival lands before reaching the observer.

## Regression and Error Museum coverage

The release includes deterministic coverage for:

1. IST arrival points toward observer for 10+ seconds then turns for IST — no false initial alert.
2. LTBA arrival remains aligned toward the observer but reaches the airport before the supposed pass — no false initial alert.
3. Destination IST with a genuine observer pass before the airport — alert remains possible.
4. Wrong destination with clear live divergence — suppression releases.
5. Destination provider unavailable — normal deterministic behavior continues.
6. ADSBDB unavailable while ADSB.lol resolves the route.
7. All destination sources unavailable — monitoring continues.
8. Slow destination lookup — monitoring path returns without waiting.
9. Fresh physical entry inside the configured radius — physical observation wins.
10. Go-around/diversion — destination metadata cannot permanently suppress a later pass.

Provider conflict, nearby-terminal conflict resolution, destination-airport-inside-radius behavior and pending-lookup active-alert behavior are also covered. The existing September 18 IST Error Museum case remains explicitly classified as a decision-level reconstruction because the full raw ADS-B track was not retained; v5.5.4 extends its expected-behavior contract without pretending it is a raw-track replay.

## Performance and cadence

A dedicated destination-path benchmark validates cached deterministic evaluation overhead and verifies that a deliberately slow background destination lookup does not leak into the monitoring path. Production cadence must also be checked after deployment against the established approximately five-second loop.

## Release-channel safety

Railway production and community/self-host stable releases are explicitly separated.

- Normal Railway CI contains Railway/application safety validation only; it does not run the long Windows ARM64/Linux ARM64/Raspberry Pi/full installer matrix.
- Railway deployment remains gated on the exact successful current `main` commit.
- The long community matrix is owned by the dedicated ChatGPT **Weekly Community Release** scheduled task and is exposed in GitHub as a manual workflow for that task to invoke when it performs the weekly release audit.
- There is no GitHub weekly cron for that matrix, and ordinary Railway pushes do not trigger it.
- Community stable publication is also manual and requires the exact commit that the ChatGPT weekly task verified through the applicable community matrix.

This Railway deployment must not be described as community-platform validated unless the separate ChatGPT Weekly Community Release task has actually completed the required community validation for the same commit.

## Prediction identity

The underlying deterministic motion and 3D proximity model is unchanged:

`5.3-3d-proximity-age-aware`

v5.5.4 changes destination-aware qualification/cancellation evidence, not the trajectory predictor itself.

## Configuration / dependencies / storage

- No new required environment variable.
- No paid API requirement.
- No AI dependency in physical alert decisions.
- No dependency change.
- No database schema or migration change.
- No service/start-command change.
- No installer prompt change is required for this Railway patch.

The provider behavior change should be recorded for the dedicated ChatGPT Weekly Community Release task so that task can decide and run the deferred community/self-host validation before publishing a community-stable v5.5.4 release.

## Rollback

If production verification finds a regression, roll Railway back to the previously healthy v5.5.3 deployment/commit. Do not move or overwrite an existing community stable tag. Any later corrected production build must use the next sequential patch version.
