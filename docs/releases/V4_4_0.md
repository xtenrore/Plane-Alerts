# Plane Alerts v4.4.0 — Reliability, Intelligence & Visual Profiles

Plane Alerts v4.4 is a reliability release built on production v4.3.2. The release keeps deterministic trajectory, CPA, ETA, route qualification and notification timing in code; AI remains outside the live decision path.

## Alert reliability

- Confirmation state now advances only on genuinely newer ADS-B observations. Repeated shared-cache evaluations cannot manufacture extra confidence or cancellation evidence.
- A cancelled encounter remains latched against predictive requalification, but a fresh aircraft physically entering the configured radius can recover normally.
- Cancellation and passed lifecycle state is committed only after the Telegram update succeeds. Failed cancellation delivery is retried instead of silently closing the alert.
- Stale observations cannot accumulate cancellation evidence.
- CPA timing is aged from the observation timestamp rather than restarted on each polling cycle, and close-pass interpolation uses squared range for a better between-sample CPA estimate.
- Terminal-arrival encounter and motion caches include the flight-number callsign so a reused airframe cannot inherit another flight's state.
- Expected-turn deadlines are fixed when the evidence first becomes actionable instead of sliding forward on every evaluation.

## Route-history isolation

Historical route intelligence remains useful as supporting veto evidence, but optional history I/O no longer sits in front of the live alert path.

- Cold and expired route-history reads return immediately from memory and refresh in bounded background work.
- Historical reads use single-flight refreshes, bounded concurrency, bounded cache size, TTLs and hard timeouts.
- Recent stale history may be reused temporarily while refresh work runs; a true cold miss safely falls back to no historical route match.
- Route-history persistence uses a fixed bounded queue with deduplication, write timeout and stale queued-work dropping.
- Provider-learning work remains on its own bounded background queue.
- Weather, upper-air and camera enrichment use bounded optional caches and safe deterministic fallbacks.

The priority ordering is therefore:

```text
ADS-B -> trajectory -> CPA -> qualification -> Telegram alert
                       |
                       +-> route/history refresh, learning, photography,
                           weather, Prediction Lab and audit telemetry
```

## Notification telemetry

Telegram edits are now explicitly separated from first notifications.

Notification history records event types including:

- `first_notification`
- `message_update`
- `cancellation_update`
- `passed_update`
- `retry`
- `failed_delivery`

`notified_at` and `first_notified_at` represent the first successful logical alert and are not refreshed by ordinary message edits. `alert_count` increments only once for that first successful alert. Delivery attempts and lifecycle updates are stored separately in a bounded event history, keeping false-positive and lead-time analysis from treating edits as new alerts.

Notification telemetry and photo snapshots are persisted after Telegram delivery through bounded background work so MongoDB latency does not delay the message itself.

## Release identity

`app/version.py` is the canonical application version source (`4.4.0`). Health, readiness, stats and worker status expose the same runtime version and commit.

The Railway deployment workflow deploys only the exact commit that passed the `main` test workflow. Because production uses `railway up`, the workflow embeds that tested SHA in `app/build_commit.txt` immediately before upload. Runtime environment commit metadata takes precedence when available; the embedded tested SHA is the deterministic fallback for CLI deployments.

## Prediction Lab and coverage safety

Prediction Lab outcome scoring remains coverage-aware. Missing ADS-B coverage is not converted into a successful forecast or a miss. Next60 historical expectations remain shadow evidence where coverage or history is insufficient.

## Verification gates

The final v4.4 reliability branch passed:

```text
python -m compileall -q app vercel_runtime worker.py
pytest -q                     # 291 passed
python scripts/benchmark_v42.py
pip check                     # no broken requirements
```

The terminal-arrival benchmark evaluated 2,250 observer/path combinations for 250 users at approximately 1,800 evaluations per second, using 9 bounded motion paths and one shared path-cache entry.

The release regression set includes fresh-observation confirmation, shared-observation duplicate prevention, production guard composition in a fresh interpreter, failed cancellation retry, recovery after a cancelled aircraft later enters the radius, stale/repeated observation behavior, IST terminal-arrival behavior, genuine close/overhead presence, route-history cold-read isolation, bounded route-history writes, and notification message-update versus first-notification semantics.

Production deployment is not considered complete until Railway reports the tested v4.4 version/commit, the worker is active at the expected cadence, Telegram is running, and logs show no notification storm or new reliability regression.
