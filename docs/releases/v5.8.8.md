# Plane Alerts v5.8.8 — Community Self-Host Reliability

## Summary

v5.8.8 is the first community stable release candidate after v5.5.3. It packages the accumulated v5.5.4–v5.8.7 reliability, storage, prediction, Telegram and Docker work, plus the post-v5.8.7 runtime fixes and the community updater/release-gate hardening.

## Cumulative changes since community v5.5.3

- Deterministic provider-first destination/path qualification and terminal-arrival safeguards, while keeping trajectory, CPA, ETA, pass/no-pass, qualification, cancellation and alert timing outside runtime AI decision-making.
- Persistent-volume storage for route history, notification lifecycle telemetry and Prediction Lab evidence. MongoDB remains the durable store for users, locations, profiles, preferences and normal application state.
- Bounded Prediction Lab spool backpressure/compaction, authenticated evidence synchronization, exact byte/hash/schema verification, repository acknowledgement before deletion, and backlog recovery that preserves unsynchronized evidence.
- Verified legacy operational-storage retirement and idempotent migration markers. Only the explicitly identified operational telemetry collections are retired; normal user/application collections are not part of that cleanup.
- Stabilized trajectory-change lifecycle behavior, provider handoffs, Next 60 history/replay and terminal-arrival filtering.
- Telegram aircraft-detail and recovery reliability, Flightradar24 aircraft links, and standalone Docker readiness using `/ready`.
- Optional repository-only maintenance and allowlisted Railway secret-synchronization workflows remain GitHub operator automation. They are not installed, required or invoked by the community self-host runtime.

## Community self-hosting updater hardening

The guided community updater now:

- selects the newest stable GitHub release only; drafts and prereleases are refused;
- refuses to overwrite tracked local source changes;
- runs offline doctor checks before changing the installation, then dependency installation and offline/live doctor checks on the target release;
- records the exact installed stable tag, commit and verification time;
- snapshots `.env`, installation metadata, setup checkpoint and the SQLite database before updating;
- restores the previous code commit and those local files if target validation or final state recording fails;
- generates a support bundle that redacts credentials and receiver coordinates.

The updater does not back up a remote MongoDB Atlas/server database. Operators must take and verify a MongoDB backup before upgrading from v5.5.3.

## Migration and upgrade notes

The cumulative v5.5.3-to-v5.8.8 upgrade includes the v5.6.x operational-storage changes:

- route history moves to the persistent-volume SQLite store;
- notification lifecycle telemetry moves to the persistent-volume SQLite store;
- Prediction Lab evidence is exported to the persistent-volume archive/spool;
- legacy operational Mongo collections are retired only through the documented migration/verification path;
- user, location, profile, preference and other normal application collections remain in MongoDB.

Before upgrading from v5.5.3, stop the old service cleanly, take a verified MongoDB backup, and preserve the Plane Alerts persistent-volume data. Do not assume checking out an older code tag reverses a completed data migration. The updater's local SQLite backup does not replace a MongoDB backup.

## Validation required for community publication

The weekly Community Release workflow is the sole owner of the long community installer/platform matrix. Publication requires:

- successful full application CI for the exact current `main` SHA;
- Linux x64 and Linux ARM64 installer/self-host tests;
- Windows x64 and Windows ARM64 installer tests;
- Raspberry Pi ARM64/QEMU platform and image validation;
- Linux x64 Docker image build, Docker Compose configuration and offline-doctor smoke;
- real MongoDB service-container migration/privacy integration;
- exact candidate checkout verification in every matrix job;
- installer asset secret/redaction scan, SHA-256 generation and post-publication checksum verification;
- immutable tag and exact tested commit verification.

The Raspberry Pi CI check is QEMU emulation, not a physical Pi 4/5 hardware test. CI uses mocked Telegram/OpenSky setup validators; it does not authenticate a real operator bot token or OpenSky credential. Those are validated during interactive setup. Do not claim physical-device or live-credential validation from CI.

## Runtime and safety boundary

- The live trajectory, CPA, ETA, pass/no-pass, qualification, cancellation and alert-timing path remains deterministic/statistical.
- Missing ADS-B coverage remains inconclusive, not a hit or miss.
- Optional maintenance automation does not control physical alert decisions.
- No AGY/Antigravity runtime or paid AI/API dependency is introduced by the community installer.
- The five-second monitoring path remains protected from blocking audit, sync and maintenance work.
