# Plane Alerts v4.8.0 — Storage, Database & Offline Resilience

v4.8.0 isolates the five-second aircraft alert path from non-critical MongoDB persistence without changing the verified physical predictor.

## What changed

- active user/profile configuration is served from a bounded last-known-good in-process image after startup validation
- active encounter/lifecycle state is memory-first and coalesced to Mongo in the background
- delayed lifecycle writes use newer-state protection so stale retries cannot overwrite a newer persisted record
- Mongo writes and status/analytics work use explicit queue limits, operation timeouts, batching/coalescing and bounded outage retry backoff
- database command timing reports read/write p50, p95, p99 and max plus failures, timeouts, retries, reconnects and queue pressure
- warm Mongo outages no longer automatically stop ADS-B ingestion, trajectory, CPA, qualification, cancellation or pass detection
- cold startup remains conservative until a valid configuration snapshot can be loaded
- health/readiness distinguish application monitoring health from optional database degradation
- Telegram settings operations return a clear temporary-unavailability response instead of exposing an internal error
- schema migration version 1 is explicit, idempotent and verified
- allow-listed export/import excludes exact locations by default, strips secret-like fields, validates schema and preserves newer records

## Queue limits

- encounter cache: 4,096
- critical encounter persistence: 4,096 coalesced records
- system status: 32 coalesced records
- optional analytical persistence: 512 coalesced records
- Mongo pool: 5 connections
- persistence operations: 1.25 s bounded timeout with exponential outage backoff

Optional work is sacrificed before the real-time alert path. Critical queue pressure is explicitly counted/logged rather than being allowed to grow without bound.

## Mongo outage behavior

A process that has already loaded verified configuration continues live aircraft monitoring from memory while Mongo is slow or temporarily unavailable. Persistence-dependent features can be delayed or unavailable and are never reported as successfully saved unless the write actually succeeds.

A cold restart during a total Mongo outage cannot safely reconstruct unknown configuration or an unpersisted delivered lifecycle state. Plane Alerts therefore stays not-ready rather than guessing.

## Migrations and export

The application now records an expected storage schema version and refuses mismatched migration identities. Migration v1 adds storage-baseline indexes for schema tracking, active/expiring approach state and profile refresh lookup.

The export/import format is intentionally not a raw Mongo dump. It allow-lists supported data, protects secrets and exact locations, rejects malformed/unsupported records and avoids overwriting demonstrably newer persisted data.

## SQLite evaluation

Mutable SQLite persistence was evaluated and intentionally deferred. The current persistence layer is Mongo-centric and a partial second backend would introduce feature divergence and restart-safety risk. The existing read-only worldwide airport/runway SQLite database remains unchanged.

## Prediction safety

`PREDICTION_VERSION` remains `4.7.3-terminal-delivery-landing-path`. v4.8 changes storage only. No runtime AI or storage subsystem gains authority over trajectory, CPA, ETA, confidence, runway use, qualification, cancellation or alert timing.

## Rollback

If v4.8 causes a production regression, roll back the main service to the exact last verified v4.7.3 production commit. Migration v1 is additive/index-only and does not destructively rewrite existing documents.
