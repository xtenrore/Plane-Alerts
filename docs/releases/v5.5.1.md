# Plane Alerts v5.5.1 — File-Backed Prediction Lab & Automated Evidence Pipeline

> Version note: `v5.5.0` was already published as the separate Guided Community Self-Hosting release. Plane Alerts release rules prohibit moving or replacing that stable tag, so this production architecture ships as the next patch, `v5.5.1`.

Plane Alerts v5.5.1 moves high-volume Prediction Lab audit, shadow-evaluation and sentinel evidence out of MongoDB and into a bounded persistent file spool synchronized to the dedicated `prediction-lab-data` Git branch.

## Architecture

- Runtime Prediction Lab evidence is written atomically under `/data/prediction_lab` on Railway and an equivalent persistent path for self-hosting.
- Evidence writes remain optional and bounded; filesystem work is offloaded from the event loop and GitHub synchronization is never performed by the live monitoring process.
- A scheduled GitHub Actions workflow transfers bounded batches to `prediction-lab-data`. It acknowledges Railway files only after a successful Git push, so failed/conflicting syncs remain resumable.
- Commits to `prediction-lab-data` cannot trigger production deployment. Production remains gated by successful tests on the exact current `main` commit.
- Durable `case_id` / `event_id` values and Collector, Investigator and Release checkpoint files support idempotent external scheduled tasks.

## MongoDB migration

The following Prediction Lab collections are exported into verified NDJSON chunks under `prediction_lab/archive/mongo-import/` and retired only after count and SHA-256 integrity checks succeed:

- `prediction_lab_audit`
- `prediction_shadow_evaluations`
- `prediction_sentinel_routes`

Normal Plane Alerts application storage is not migrated by this release. User, profile, preference, route-history, approach-state and configuration data remain in the configured database. `flight_route_samples` remains normal product data and is used by `/next60` history forecasts.

The migration is part of actual database startup, not an operator-only helper. It runs before normal application index/schema startup. Atlas quota-full index maintenance may be deferred only long enough to export and retire the verified Prediction Lab collections; an unverified migration, a non-quota database error, or a database that remains quota-full after the retirement blocks storage readiness instead of being silently accepted.

## Evidence and evaluation

Evidence records preserve release/prediction version, trajectory observations, CPA/ETA/confidence evolution, qualification and route suppression state, lifecycle outcomes, observed closest pass, provider provenance/freshness and deterministic diagnostic fields.

Missing or stale ADS-B coverage remains inconclusive and is never scored automatically as a hit or miss. The 30–60 minute `/next60` horizon remains shadow/evaluation-only; live deterministic CPA remains authoritative. `/next60` subsequent-reality records are coverage-aware and do not convert missing observation coverage into a hit or miss.

The fixed high-risk sentinel network remains Istanbul, London, Frankfurt, Paris, Amsterdam, Madrid, Rome and Vienna. Locations configured for users who currently have delegated admin access are also sampled in memory. Repository evidence stores only privacy-safe salted region identifiers for those private locations and does not include admin identity or private observer coordinates.

## `/next60`

Historical `/next60` candidates are now derived from bounded normal `flight_route_samples` instead of `prediction_lab_audit`. Live deterministic `approach_states` still override historical candidates for the same aircraft/flight. History evidence is recorded as shadow-only and later missing coverage remains inconclusive.

## Self-hosting and installer continuity

The guided installer from the already-published v5.5.0 community release is carried forward into v5.5.1 so the newest stable release remains installable on Linux x64, Linux ARM64, Raspberry Pi ARM64, Windows x64 and Windows ARM64. Stable release publishing attaches all six installer entry points plus `SHA256SUMS.txt` and verifies them before considering the release published.

Native guided installs can use the persistent SQLite backend or MongoDB. Docker Compose explicitly remains on its bundled MongoDB service and adds the persistent `prediction_lab_data` volume mounted at `/data/prediction_lab`. Native Prediction Lab evidence uses a persistent community-data path rather than Railway's `/data` convention. Existing normal application data is preserved across supported updates.

No new paid API or runtime AI dependency is introduced. The physical prediction version remains `5.3-3d-proximity-age-aware`; trajectory, CPA, ETA, qualification, cancellation and alert timing are unchanged.

## Update and rollback

Upgrade from v5.4.3 normally. Keep the previous stable tag/commit and database backup until the v5.5.1 migration and production health checks are confirmed. Rollback code target is v5.4.3 (`2546e0ff854ce32511b4c358ba162e842397ff66`). If the legacy Prediction Lab Mongo collections have already been retired, v5.4.3 can still run normal application behavior, but historical Lab telemetry will remain in the v5.5 file archive rather than being restored automatically to MongoDB.
