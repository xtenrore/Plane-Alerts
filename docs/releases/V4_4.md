# Plane Alerts v4.4.0

Release date: 2026-09-20

v4.4 is a reliability-focused release built on the v4.3.2 production line. It keeps live trajectory, CPA, ETA and alert timing deterministic while tightening observation confirmation, terminal-arrival handling, monitoring-path latency, notification telemetry and deployed-version reporting.

## Reliability changes

### Route-history I/O is no longer alert-critical

Cold or expired flight-number history no longer waits on MongoDB in front of a live alert. The evaluator immediately uses cached history when safe or an empty fallback on a true cold miss, then starts one bounded background refresh per callsign. Refresh count, concurrency, cache size, TTL and database wait time are bounded.

Route-history persistence remains behind a fixed worker queue with deduplication, write timeouts and stale-work dropping. Provider learning is also off the five-second critical path.

### Fresh observations control confirmation

Qualification confirmation advances only on a newer aircraft observation. Reprocessing the same ADS-B sample for another user or another scheduler pass cannot manufacture another confirmation. Long observation gaps reset incomplete confirmation state.

Fresh independent physical observations can recover a genuine in-radius pass when a prediction is otherwise uncertain. Single, stale, duplicate or moving-away evidence does not receive that promotion.

### Terminal-arrival and cancellation behavior

The IST/terminal-arrival ensemble continues to suppress straight-line false positives when destination and airport-convergence evidence indicate the aircraft should turn away before the observer CPA.

Expected-turn evidence cannot permanently hide a genuine close pass. When the expected turn does not occur, live motion regains authority. A confirmed cancellation is latched against immediate predictive requalification, while fresh physical entry into the configured radius releases the latch.

A failed Telegram cancellation delivery no longer closes the encounter. The active alert remains persisted and the cancellation is retried on the next qualifying evaluation.

### Notification telemetry

Notification history now distinguishes first notifications from normal lifecycle edits. Recorded event types are:

- `first_notification`
- `message_update`
- `cancellation_update`
- `passed_update`
- `retry`
- `failed_delivery`

`notified_at` and `first_notified_at` represent the first successful logical alert. Message edits do not refresh them and do not increment `alert_count`. Failed deliveries are recorded separately. Telemetry and photo snapshots run after Telegram delivery through bounded background work.

### Release identity

`app/version.py` is the canonical application-version source. Health, readiness, worker status and system reporting expose v4.4.0 plus the deployed commit SHA.

The Railway workflow deploys only after successful `main` CI, checks out the exact tested SHA, writes that SHA into ephemeral build metadata immediately before upload, and deploys that exact tree to the main and AGY services. The generated commit file is ignored by git so a previous release SHA cannot become stale source metadata.

## Prediction and audit safeguards

Prediction Lab outcome handling remains coverage-aware: missing ADS-B observations are unresolved rather than counted as successful predictions or misses. Bounded outcome windows prevent another same-day occurrence of the same callsign from being mistaken for the forecasted occurrence.

30–60 minute expectations remain shadow-only.

## Release verification before merge

The final reliability branch passed:

- Python compile/static import check
- 287 pytest unit/regression/replay tests
- v4.2 terminal-arrival benchmark
- dependency consistency with `pip check`

The terminal-arrival benchmark on the final pre-documentation gate evaluated 2,250 observer/path combinations for 250 users at approximately 1,548 evaluations per second while reusing one bounded shared motion-path cache entry.

Regression coverage includes:

- fresh-observation confirmation
- repeated/duplicate observation protection
- failed cancellation retry
- cancelled encounter recovery after fresh radius entry
- stale ADS-B behavior
- IST expected-turn suppression
- genuine close-pass recovery
- notification update versus first-notification accounting
- cold route-history read isolation
- bounded route-history writes
- existing Error Museum and Next60 outcome cases

## Deployment policy

The Railway AI agent is not used. The release is deployed only from a successful tested `main` commit. Production verification must confirm health, readiness, Telegram runtime, monitoring cadence, reported v4.4.0 version, exact commit SHA, absence of a notification storm and clean application logs.
