# Plane Alerts v5.8.1 — Telegram Detail and Recovery Reliability

## Problem and changes

The v5.8.0 tracker-link update renamed the Next 60 helper to `_tracker_url`, but the latency wrapper installed during application startup still called `_adsb_url`. Selecting More Info for a matching aircraft therefore raised `AttributeError`. Regression tests reproduce the failure through the registered production callback, rather than testing only the renderer or the original callback it replaces.

- The installed callback now sends the aircraft detail and correct Flightradar24 button. Callsign, history-only, ICAO24-only and unavailable-link cases are covered.
- Failed or cancelled detail attempts release their duplicate-update marker so a retry can proceed. Confirmed successful delivery remains deduplicated. Callback acknowledgement still precedes database work.
- Successful acknowledgement bookkeeping only retains tracked callback IDs, which already have a bounded count and expiry. Duplicate receipt preserves first-receipt timestamp order. Failed acknowledgements no longer produce successful latency samples.
- Unexpected Telegram errors now provide a short retry/help message. Diagnostics record exception class and at most eight application module/function/line locations, excluding exception text, source lines, local variables, message contents and private coordinates. Error-notice failures are contained and task cancellation propagates.

Production logs on 26 September recorded two opaque Telegram `AttributeError` failures. Those logs do not identify the originating callback, so they cannot independently establish that both events were this bug; the installed-callback regression is directly reproduced from the deployed source.

## Safety and validation

The change affects Telegram detail/recovery and callback bookkeeping. Physical prediction version remains `5.3-3d-proximity-age-aware`; aircraft ingestion, trajectory, CPA, ETA, qualification, cancellation and alert timing are unchanged. No paid AI/API dependency is added.

Release gates are the targeted Telegram/recovery regressions, the full application suite, existing Railway replay and performance gates, dependency consistency, exact-commit GitHub CI and post-deploy health/log/cadence verification. Tests mock Telegram transport and do not send synthetic messages to production users.
