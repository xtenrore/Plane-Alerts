# Plane Alerts v5.8.3 — Dead Workflow Cleanup

## Scope

This release completes Release 2 of the Architecture & Product Improvement roadmap: remove dead/misleading workflow files and make the active Vercel workflow implementation unambiguous.

Before this release, the repository contained both `vercel_runtime/plane_workflows.py` and `vercel_runtime/plane_workflows_fixed.py`. The actual Vercel ingress imported `plane_workflows_fixed`, and `vercel_runtime/pyproject.toml` registered `plane_workflows_fixed:wf`, while the stable-looking `plane_workflows.py` still contained the retired v3.2 durable graph. That layout was misleading even though production wiring selected the newer implementation.

v5.8.3 moves the exact active v3.3 workflow implementation to the stable `vercel_runtime/plane_workflows.py` filename, updates all active ingress/packaging references, removes `plane_workflows_fixed.py`, and removes the retired v3.2 workflow implementation rather than preserving a second authority.

## Behavior preservation

The durable Vercel workflow namespace remains `planev33`; this release does not reuse the retired `planev32` namespace and therefore does not reinterpret old durable workflow histories under a different graph.

The existing v3.3 behavior is preserved:

- Telegram callback queries are acknowledged through the webhook response before slower durable processing completes;
- normal and detached photo/conditions updates continue through `process_telegram_update_v33`;
- the warm Telegram application and Mongo client reuse remain in `plane_runtime_support.py`;
- monitor cycles continue to use the v3.3 workflow graph and existing bounded cadence;
- GitHub-OIDC bootstrap/verification semantics are unchanged apart from importing the canonical module name.

The Plane Alerts physical prediction identity remains `5.3-3d-proximity-age-aware`. No trajectory, CPA, ETA, destination/path qualification, cancellation, alert timing, provider selection, Telegram user feature, or Railway runtime behavior is intentionally changed.

## Regression and architecture coverage

The existing Vercel latency regression suite now reads the canonical workflow plus `plane_runtime_support.py` instead of depending on both old and new workflow files. A dedicated architecture regression verifies:

- `vercel_runtime/plane_workflows.py` exists;
- `vercel_runtime/plane_workflows_fixed.py` does not exist;
- Vercel ingress imports `plane_workflows`;
- `pyproject.toml` registers `plane_workflows:wf`;
- the canonical module uses `Workflows(namespace="planev33")` and not `planev32`;
- active Vercel/runtime/test/build source cannot reintroduce the obsolete `plane_workflows_fixed` reference.

Required Railway release validation remains the repository's compile/static checks, full pytest suite, all focused regression/replay suites, performance benchmarks, dependency consistency, exact-tested-main gating, Railway deployment, and production readiness/log/cadence verification.

## Installer and community impact

The installer/self-host configuration surface is unchanged. This release does not change `.env` variables, Python dependencies, MongoDB or SQLite schema, provider credentials, OpenSky configuration, local ADS-B setup, Telegram bot setup, process start commands, Railway health endpoints, Docker/installer files, or updater/rollback behavior.

COMMUNITY IMPACT: custom downstream code that imported `vercel_runtime/plane_workflows_fixed.py` by filename must use the stable `plane_workflows.py` name instead. The official Railway runtime and community self-host process do not use that obsolete module name. Full Windows ARM64, Linux ARM64, Raspberry Pi, installer and updater validation remains deferred to the weekly Community Release workflow; this Railway release does not claim those platform matrices were rerun.
