# Plane Alerts v5.6.1 — Persistent Operational Storage

## Scope

v5.6.1 is an emergency Railway reliability patch for MongoDB Atlas quota exhaustion. It does not change the deterministic trajectory, CPA, ETA, destination-path qualification, cancellation, or alert-timing model.

## Storage boundary

MongoDB remains authoritative for durable application and user state, including users, Telegram identity, configured locations, profiles, alert preferences/settings, and other durable configuration.

High-volume operational data is permanently excluded from MongoDB in Railway production. Callsign route-history samples now use the existing Plane Alerts persistent volume under `/data/prediction_lab/runtime/route_history.sqlite3`. Prediction Lab audit/shadow/sentinel evidence remains file-backed under the same Plane Alerts-owned persistent volume and its compatibility writer is prevented from falling back to MongoDB.

No retired external-agent/AGY runtime or volume is restored or reused.

## Route-history retention

The SQLite route-history store is bounded to 35 days of retention and at most 360 points per callsign/day. Reads are limited to the established 28-day lookback and 28 route-day paths. Disk reads/writes run outside the five-second monitor thread through bounded background work.

## Atlas recovery

After the volume has accepted live route data, v5.6.1 starts a background migration of useful recent `flight_route_samples` rows to the persistent volume. It then retires only the legacy `flight_route_samples` Mongo collection. User/profile/location/settings collections are not part of this cleanup.

The existing Prediction Lab migration remains responsible for exporting and retiring its own explicitly legacy operational collections. New Prediction Lab/sentinel writes cannot fall back to Mongo while that historical cleanup is pending.

## Failure behavior

Persistent-volume route-history failures are optional/supporting failures: they do not control live CPA or delay the five-second aircraft monitor. Repeated volume failures are summarized/rate-limited rather than producing one full traceback per aircraft.

## Validation requirements

Before Railway deployment, the exact commit must pass targeted operational-volume regression tests, affected route-history and Next 60 tests, prediction/destination Error Museum coverage, cadence/performance checks, and required GitHub CI. Production verification must confirm the exact deployed SHA, mounted Plane Alerts volume, disappearance of `flight_route_samples` Mongo quota errors/log storms, preserved user/location/profile behavior, and healthy five-second monitoring cadence.
