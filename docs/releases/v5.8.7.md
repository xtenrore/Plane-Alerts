# Plane Alerts v5.8.7 — Docker Monitoring Readiness

## Change

The standalone Dockerfile health check queried `/health`, which returns HTTP 200 with a JSON `application_ready: false` when live monitoring is degraded. Docker Compose and the configured Railway service already query `/ready`, which returns HTTP 503 for that state.

The Docker image now checks `/ready`. A regression verifies that degraded readiness returns 503 and healthy readiness returns 200, and checks both Dockerfile and Compose targets. No live prediction, provider, Telegram, storage-schema or monitoring-loop behavior changes.

## Validation and community impact

The Railway release requires full application CI, readiness regression, exact tested main deployment, production health, maintenance and cadence checks. COMMUNITY IMPACT: standalone self-host Docker image health semantics change. Standalone image/container smoke tests and the full cross-platform installer matrix remain assigned to the weekly Community Release workflow; this Railway release does not claim they ran. Railway's existing service `healthcheckPath` was already `/ready` and is unchanged.

## Community self-hosting updater hardening

The guided community updater now records the exact installed stable tag and commit after both offline and live doctor checks. Its pre-update snapshot includes `.env`, installation metadata, setup checkpoint and the SQLite database when SQLite is selected. If target validation or final state recording fails, rollback restores the previous code commit and those local files.

Regression coverage exercises stable-tag update identity, dirty tracked-tree refusal, failed-update rollback, Telegram/OpenSky/local-receiver configuration validators, and support-bundle redaction. A dedicated community CI job exercises the real MongoDB Prediction Lab migration against an isolated MongoDB service. MongoDB itself remains an operator-managed backup responsibility; the updater does not snapshot Atlas or another MongoDB server.

These are community-only installer and validation changes. They do not alter the Railway runtime, live trajectory/CPA/ETA decisions, notification lifecycle, storage schema or five-second monitoring loop.
