# Plane Alerts v5.6.10 — Authenticated Prediction Lab Spool Bridge

## Why this patch exists

The v5.6.7–v5.6.9 storage-recovery work proved two separate Railway CI file-transfer limitations in production: selected-volume file listing failed, and the live-service SFTP interface then required a user SSH key that a project-token GitHub runner does not possess. Both failures happened before repository acknowledgement or remote deletion, so unsynced Prediction Lab evidence remained intact.

v5.6.10 removes Railway SFTP from the evidence synchronization path entirely.

## What changed

Plane Alerts now exposes a narrowly scoped, HTTP Basic-authenticated administrative synchronization bridge under the existing `/admin` authentication boundary.

The bridge:

- exports only `prediction_lab/raw` JSON/NDJSON evidence;
- validates the Plane Alerts evidence schema before export;
- rejects credential-like material;
- caps each batch at 500 files and 25 MiB;
- packages the batch in ephemeral `/tmp` storage rather than consuming the already-full persistent volume;
- publishes a manifest containing exact repository-relative path, byte length and SHA-256 for every object;
- never deletes data during export;
- accepts acknowledgement only for `raw/` paths that remain inside the Prediction Lab root;
- rechecks exact byte length and SHA-256 immediately before unlinking each acknowledged object.

The GitHub synchronization workflow independently validates the ZIP member set, path boundaries, size cap, SHA-256, JSON/NDJSON syntax, Plane Alerts evidence schema and credential pattern. It then commits/pushes the exact bytes to `prediction-lab-data`. Only after that push succeeds does it POST the exact manifest back to the runtime acknowledgement endpoint.

The workflow uses the existing Railway project token only to retrieve the already-configured `ADMIN_PASSWORD` and public service domain. The password is masked immediately and is not written to repository content. No Railway SSH key, new runtime GitHub credential or paid service is introduced.

## Deployment-race protection

A merge starts the sync workflow before Railway may have finished deploying the new application build. The workflow therefore polls the authenticated status endpoint and refuses to export anything until the running bridge reports exactly `5.6.10`.

This keeps the merge-triggered recovery tied to the exact deployed release instead of accidentally talking to the previous runtime.

## Safety boundaries

This incident-recovery bridge is deliberately **raw-evidence only**. It cannot select route-history SQLite, notification-history SQLite, state files, user/profile/location/settings data, or the historical Mongo archive.

A failed download, ZIP validation, repository rebase, Git push, acknowledgement hash check or path check leaves the corresponding raw evidence intact.

The five-second aircraft monitor does not call this bridge. Filesystem packaging and acknowledgement run through worker threads outside the alert-critical path.

## Prediction behavior

There is no change to trajectory, CPA, ETA, confidence, destination/path qualification, cancellation, pass/no-pass or notification timing.

The physical prediction version remains:

`5.3-3d-proximity-age-aware`

## Production verification required

v5.6.10 is complete only after all of the following are observed on the exact tested production commit:

1. `/ready` and the Telegram runtime remain healthy.
2. The authenticated bridge reports version `5.6.10`.
3. A non-empty batch is independently validated and committed to `prediction-lab-data`.
4. Runtime acknowledgement removes exactly the repository-verified batch.
5. Persistent-volume free space increases from the zero-headroom incident state.
6. Route-history and notification-history SQLite writes recover without new `OperationalError` failures.
7. Monitor timing remains effectively on the configured five-second cadence.
8. Chained bounded passes continue while the raw backlog remains large and stop when the batch falls below the continuation threshold.
