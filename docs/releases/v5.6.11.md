# Plane Alerts v5.6.11 — Resilient Prediction Lab Spool Drain

## Production evidence

The v5.6.10 HTTP synchronization bridge deployed successfully and authenticated correctly, but the first real batch request returned HTTP 409 before Git validation, repository push or runtime acknowledgement. The live bridge simultaneously reported `free_bytes=0`, and Railway logs still showed `sqlite3.OperationalError: database or disk is full` in notification telemetry. No raw evidence was deleted by the failed attempt.

v5.6.7 compaction already caps NDJSON bundles at 8 MiB, below the bridge's 25 MiB batch limit. The safer recovery correction is therefore to prevent an isolated malformed, legacy, sensitive, unreadable or oversized raw object from blocking valid evidence behind it.

## Changes

The authenticated Prediction Lab bridge now scans a bounded maximum of 5,000 raw objects while selecting at most 500 files / 25 MiB for one transfer.

Objects that cannot safely be exported are left untouched on the Railway volume and counted by a sanitized reason class. Supported reason classes include schema, invalid JSON, empty bundle, credential-like content, read/stat error, path escape, oversized and generic validation error. File contents and secret-like material are never emitted in workflow diagnostics.

A rejected object no longer terminates a batch when valid evidence is available later in the bounded scan. If a bounded scan contains no exportable evidence at all, the bridge returns a sanitized summary such as a rejection class/count rather than exposing the object contents.

The manifest now also records the bounded scan count, rejected count/reasons and files deferred by the current batch-byte limit. GitHub still independently verifies the member set, repository-relative `raw/` path boundary, byte count, SHA-256, JSON/NDJSON schema and credential-safety rule before staging or committing anything.

## Destructive boundary remains unchanged

No runtime deletion occurs during export.

Only after the exact evidence bytes are present on `prediction-lab-data` does GitHub POST the accepted path + byte count + SHA-256 acknowledgement. The runtime rechecks each file immediately before unlinking it. Malformed/legacy/sensitive/oversized objects skipped during export are never included in acknowledgement and remain untouched.

Route-history SQLite, notification-history SQLite, state, user/profile/location/settings data and historical archive data remain structurally outside the bridge's selectable raw tree.

## Diagnostics

The workflow now captures the HTTP status from the bridge batch request and, on failure, prints only the bridge's sanitized `detail` field. This prevents another 409 from hiding the rejection class while avoiding exposure of raw evidence or credentials.

## Prediction behavior

There is no change to trajectory, CPA, ETA, confidence, destination/path qualification, pass/no-pass, cancellation or notification timing.

The physical prediction version remains:

`5.3-3d-proximity-age-aware`
