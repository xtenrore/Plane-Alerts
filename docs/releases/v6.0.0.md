# Plane Alerts v6.0.0 — Main-Based Diagnostic and Fix Plan Release (v6)

## Summary

Plane Alerts v6.0.0 (`v6`) executes the **Main-Based Diagnostic and Fix Plan** directly on top of the current `main` branch (`v5.8.8` baseline, pinned commit `b86310def623a3dec891677d143066e066354aaa`). Inherited Error Museum records and historical scheduled Prediction Lab outputs are treated strictly as unverified historical context rather than ground truth.

All live alert decisions remain 100% deterministic/statistical (`PREDICTION_VERSION = "5.3-3d-proximity-age-aware"`), while adding explainable runway-threshold airport/arrival detection, curvature-aware terrain line-of-sight (LOS) visibility, age-aware ETA/CPA root-cause attribution, privacy-safe Phase 1 decision diagnostics, and denominator-explicit Phase 4 release metrics.

## Phase 1 — Main-Based Diagnosis Without Changing Alert Decisions

- **Defect**: Previous telemetry lacked a unified, privacy-safe per-evaluation record that could explain both a real notification and a real suppression from fresh observations without mutating live alert qualification, suppression, cancellation, ETA, CPA, or notification timing.
- **Evidence**: Fresh evaluations on pinned `main` required correlation across separate route-guard, 3D proximity, and provider freshness logs.
- **Behavior change (`app/intelligence/diagnostics_v6.py`)**:
  - Added `DecisionDiagnosticRecord` and `DiagnosticCollectorV6` capturing:
    1. Observation timestamp, source, age/freshness (`fresh`, `aging`, `stale`, `missing_unknown`), privacy-hashed observer reference (`obs_<sha256>`), relative distance/bearing, altitude, heading, and track history length;
    2. Predicted horizontal CPA, 3D CPA, age-aware ETA, confidence, uncertainty, and trajectory evidence used;
    3. Airport/arrival classification and its explicit reason code and human-readable explanation;
    4. Terrain line-of-sight result (`clear`, `blocked`, or `unknown`) plus terrain-data version and quality;
    5. Final decision (`alert`, `suppress`, `cancel`, `hold`, `unknown_coverage`, or `delivery_failure`) plus a stable reason code;
    6. Structured 5-way user feedback (`saw_it`, `terrain_blocked`, `poor_visibility`, `wrong_timing_path`, or `unsure`) wired into `app/bot/feedback.py`.
  - Exact observer coordinates and credentials are never stored in diagnostic records.
  - Bounded retention (`OrderedDict` ring buffer, default 2,048 records) and safe runtime disable toggle (`PLANE_DIAGNOSTICS_V6_ENABLED=0`).
  - Missing or stale ADS-B coverage is strictly recorded as `unknown` (`coverage_status="unknown"`), never as a confirmed hit or miss.

## Phase 2 — Triage of Fresh Failures Into Five Distinct Problem Classes

- **Defect**: Treating "bad alert" as a single undifferentiated defect conflates stale data, kinematic turns, terminal operations, terrain blockage, and notification delivery issues.
- **Evidence**: Fresh audit cases on pinned `main` separate cleanly when evaluated by physical root cause.
- **Behavior change (`triage_fresh_case` in `app/intelligence/diagnostics_v6.py`)**:
  - Classifies each fresh case into one of five canonical problem classes while preserving `main_sha`, `observed_inputs`, `commit_behavior`, and `expected_result`:
    1. `DATA_FRESHNESS` — stale, missing, or conflicting ADS-B observations;
    2. `ETA_TRAJECTORY` — observation age correction, speed/altitude changes, turns, or kinematic uncertainty;
    3. `AIRPORT_LOGIC` — departure, arrival, holding, missed approach, or airport-nearby traffic misclassified;
    4. `TERRAIN_VISIBILITY` — predicted pass geometrically hidden by terrain from the observer location;
    5. `NOTIFICATION_LIFECYCLE` — duplicate, late, wrongly cancelled, or undelivered alert.

## Phase 3 — Verified Cause Fixes

### A. Explainable Airport and Arrival Detection (`app/intelligence/airport_arrival_v6.py` & `app/intelligence/route_guard.py`)

- **Defect**: Nearest-airport or destination-label heuristics alone cannot explain which runway geometry matched or guarantee that a genuine observer pass occurring *before* the runway threshold remains unsuppressed.
- **Evidence**: Controlled terminal scenarios around multi-runway airports (e.g., `LTFM` Runway `17L/35R`) comparing final approach before observer, observer pass before runway threshold, climbing departure, holding orbit, and missed approach / go-around.
- **Behavior change**:
  - `match_runway_threshold()` and `evaluate_airport_arrival_v6()` evaluate aircraft against compiled OurAirports + override runway thresholds, reciprocal headings, extended centerlines ($\le 1.85\text{ km}$ lateral offset, $\le 22^\circ$ alignment), altitude AGL, vertical rate, and multi-sample track turn/divergence history.
  - Produces explainable classifications (`ARRIVAL`, `DEPARTURE`, `HOLDING`, `MISSED_APPROACH`, `OVERFLIGHT`, `AIRPORT_NEARBY`) with explicit matched airport/runway geometry and track evidence.
  - **Genuine observer pass protection**: If the aircraft passes the observer's alert radius before reaching the runway threshold (`observer_passed_before_runway=True`), or if a climbing go-around (`MISSED_APPROACH`) is detected, suppression is explicitly prevented/released.

### B. Terrain Line-of-Sight Visibility (`app/intelligence/terrain_visibility_v6.py`)

- **Defect**: Low-altitude passes behind intervening ridges can be geometrically hidden from the observer, while missing or coarse elevation data must never fabricate a blockage.
- **Evidence**: Geometric ray-elevation comparison along observer-to-aircraft elevation profiles with $4/3$ effective Earth-radius curvature drop ($R_{\text{eff}} \approx 8495\text{ km}$).
- **Behavior change**:
  - `evaluate_terrain_line_of_sight()` computes the sightline elevation angle from observer elevation to aircraft altitude and compares it against intermediate terrain samples adjusted for Earth curvature (`earth_curvature_drop_m()`).
  - Returns `blocked` **only** when verified high/medium-resolution terrain data ($\le 180\text{ m}$ spacing, $\le 3.5\text{ km}$ sample gap) proves a ridge exceeds the sightline above the safety margin.
  - Returns `unknown` whenever observer elevation, aircraft altitude, or DEM profile data is missing, sparse, or coarse.
  - Keeps geometric terrain obstruction strictly distinct from clouds, haze, buildings, trees, and local visual conditions via `visual_condition_disclaimer`.

### C. Age-Aware ETA and CPA Attribution & Confirmed-Pass Scoring (`app/intelligence/eta_cpa_v6.py`)

- **Defect**: Discretized path steps can introduce step-boundary jitter in radius-entry ETA, and scoring ETA accuracy on uncovered or missing-ADS-B passes distorts error metrics.
- **Evidence**: Sub-step entry interpolation tests and root-cause attribution across stale samples (`OLD_OBSERVATIONS`), active turns (`CHANGING_TRAJECTORY`), terminal path shifts (`AIRPORT_PATH_HANDLING`), and delivery latency (`DELIVERY_TIMING`).
- **Behavior change**:
  - `refine_age_aware_radius_entry_s()` performs sub-step linear interpolation across the alert-radius boundary and subtracts provider-reported observation age while preserving `PREDICTION_VERSION = "5.3-3d-proximity-age-aware"` and all v5.3/v5.1 confidence and uncertainty safeguards.
  - `diagnose_eta_cpa()` attributes ETA/CPA residuals to their primary physical cause.
  - `evaluate_confirmed_pass_eta_error()` scores ETA error (`abs_eta_error_s`) strictly on confirmed observed in-radius passes and marks uncovered or stale-coverage cases `inconclusive`.

## Phase 4 — Validation Metrics, Denominators, and Known Limitations

`compute_v6_success_measures()` in `app/intelligence/diagnostics_v6.py` computes all six release validation families with explicit numerators, denominators, and unknown/uncovered counts:

1. **Confirmed false alerts per observer-hour**: Count of confirmed false alerts divided by observed hours, with unknown-coverage alerts reported separately (`false_alert_unknown_coverage_count`).
2. **Confirmed missed visible passes**: Count of missed alerts among confirmed in-radius passes with `terrain_los_status == "clear"`, with unknown visibility/coverage reported separately (`visibility_unknown_coverage_count`).
3. **ETA error (MAE and P90) on confirmed observed passes**: Computed strictly over `eta_confirmed_passes_denominator`, alongside `eta_unavailable_or_uncertain_count` and `eta_unavailable_share`.
4. **Airport classification errors separated by class**: Breakdown of `errors`, `total_confirmed`, and `unknown_coverage` across `ARRIVAL`, `DEPARTURE`, `OVERFLIGHT`, `HOLDING`, `MISSED_APPROACH`, and `AIRPORT_NEARBY`.
5. **Terrain false-clear rate and terrain unknown rate**: Explicit `terrain_false_clear_count / terrain_confirmed_obstructed_denominator` and `terrain_unknown_count / terrain_total_evaluated_denominator`.
6. **Alert delivery/cancellation errors and monitoring-loop health**: Duplicate sends, wrong cancellations, delivery failures over `lifecycle_events_denominator`, plus `monitoring_loop_healthy` and `monitoring_loop_p95_cycle_ms`.

### Known Limitations

- Geometric terrain line-of-sight evaluates terrain elevation profiles and Earth curvature only; it does not model clouds, haze, rooftop buildings, or vegetation, and returns `unknown` where high-resolution DEM coverage is unavailable.
- Missing or stale ADS-B coverage remains `unknown` / `inconclusive` and cannot be scored as a confirmed physical pass or miss.

## Community self-hosting matrix corrections

- Empty optional values in `.env` and `.env.example` are treated as unset, preserving validated Pydantic defaults for numeric timeouts, monitoring cadence, radius, database name and host during fresh Docker Compose setup.
- Removed the unused `google-genai` SDK from the native self-host dependency lock. Current Gemini integrations use direct `httpx` REST calls; this avoids an unnecessary `google-auth` / `cryptography` transitive source build on native Windows ARM64.
- Windows x64 and ARM64 PowerShell dependency steps now check every `pip` exit code immediately, preventing a later test-package install from masking a failed runtime dependency install.
- Corrected the v6.0.0 baseline pin to the existing v5.8.8 main checkpoint and require the publication gate to verify that it resolves within the tested main history.

## Community self-hosting updater hardening

The guided community updater continues to enforce all v5.8.8 self-hosting protections when upgrading to or rolling back from `v6.0.0`:

- selects the newest stable GitHub release only; drafts and prereleases are refused;
- refuses to overwrite tracked local source changes;
- runs offline doctor checks before changing the installation, then dependency installation and offline/live doctor checks on the target release;
- records the exact installed stable tag, commit and verification time;
- stops the running community service before snapshotting or replacing code;
- snapshots `.env`, installation metadata, setup checkpoint and the SQLite database before updating, resolving relative SQLite paths against the installation root;
- restores the previous code commit (`v5.8.8` or `v5.5.3`) and those local files if target validation or final state recording fails;
- generates a support bundle that redacts credentials and receiver coordinates.
